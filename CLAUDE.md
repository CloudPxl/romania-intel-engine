# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

This is a monorepo with two independently-versioned projects:

- `romania-intel-engine/` — Python/FastAPI backend (the deployed product API).
- `romania-intel-frontend/` — Next.js 16 / React 19 frontend, checked in as a **git submodule** with its own `.git`. Commit and push inside that directory separately from the root repo, then commit the bumped gitlink at the root. It was for a long time a gitlink (mode 160000) with **no `.gitmodules`**, which meant `git submodule status` failed and a fresh clone of the monorepo produced an empty `romania-intel-frontend/` that `git submodule update --init` could not populate; the mapping now exists, so don't delete it.

The repo root is now deliberately near-empty — `CLAUDE.md`, `README.md`, `.gitignore`, `.github/`, `create_clean_zip.sh`, and the two project directories. It used to also carry ~14 large one-off `deploy_*.py`/`fix_*.py`/`setup_*.py` code-generation scripts (throwaway patchers that bulk-wrote files into the two project directories during earlier sessions), a stray `package.json`/`package-lock.json` from an `npm install` run in the wrong directory, and four zero-byte files (`Build`, `next`, `193`, `my-project@0.1.0`) from a mangled shell command. All of that was deleted — it was unreferenced by any code, workflow, or config, and is recoverable from git history if ever needed. **Don't recreate that pattern**: edit files in `romania-intel-engine/` and `romania-intel-frontend/` directly rather than writing generator scripts at the root. A root `node_modules/` (just `@supabase/supabase-js` + `lucide-react`) may still exist on disk from that same misplaced install; it is gitignored and safe to `rm -rf`.

## Commands

### Backend (`romania-intel-engine/`)

```bash
python -m venv ../venv && source ../venv/bin/activate   # first-time setup (venv lives at repo root)
pip install -r requirements.txt

python server.py                    # run the production API (uvicorn, reads PORT env, defaults to 8000)
python daemon.py                    # standalone 6-hourly ingestion scheduler (no HTTP server). NOT deployed,
                                      # and it still calls the legacy run_pipeline() rather than run_tick() —
                                      # so it writes opportunities but records no tick, leaving
                                      # /api/v1/system/status permanently reporting is_stale. Fix or delete
                                      # before relying on it.

python scripts/verify_backend_health.py   # hit the deployed Render API + Postgres and report health

pytest                               # runs tests/ (pytest.ini sets asyncio_mode=auto) — 10 files covering
                                      # the CMS adapters, TED scraper, document worker, ranked feed,
                                      # onboarding, auth identity, CORS error responses, LLM prompt budget
                                      # and caiet extraction, plus the original
                                      # direct-acquisition scraper; no DATABASE_URL needed, persistence
                                      # degrades to a no-op the same way it does in production
```

There is still no CI. Beyond the `pytest` suite above (added alongside the SEAP direct-acquisition scrapers — see below), verify other changes by running the relevant script above or by hitting the FastAPI routes directly (`python server.py` then `curl localhost:8000/...`).

### Frontend (`romania-intel-frontend/`)

```bash
npm run dev          # next dev, expects backend on http://localhost:8000
npm run build
npm run start
npx tsc --noEmit     # typecheck — no lint/test script is configured, no CI; build + this are the only verification
```

## Architecture

### The ingestion pipeline

`scrapers/orchestrator.py:OpportunityOrchestrator` fans out to 15 scrapers (22 when `ENABLE_LIVE_ELICITATIE=true`, `ENABLE_LIVE_DIRECT_ACQUISITION=true`, `ENABLE_LIVE_CONTRACT_NOTICES=true`, `ENABLE_LIVE_COUNTY_REGISTRY=true`, and `ENABLE_LIVE_TED=true`, all five of which `render.yaml` sets by default) under `scrapers/matrix/*_scrapers.py`, each extending `scrapers/base_scraper.py:BaseScraper`. **These are real live scrapers, not fixtures** — every one does genuine `httpx`/BeautifulSoup/PDF-table extraction against a specific verified source (a JSON API, a WordPress REST endpoint, a server-rendered listing page, a PDF register) and honestly reports zero signals rather than fabricating data when a source is unreachable or has no real feed (e.g. `CnairCfrScraper`, `ApmPermitScraper`). The matrix is not an even grid across domains — it's whatever real sources exist per domain, plus `elicitatie_scraper.py:ElicitatieLiveScraper` (live SICAP/e-licitatie market consultations), `direct_acquisition_scraper.py:DirectAcquisitionScraper`/`DaAwardNoticeScraper` (live SEAP direct-purchase notices and their award notices), `notice_scraper.py:ContractNoticeScraper`/`SimplifiedContractNoticeScraper` (live SEAP full-tender Contract Notices and Simplified Contract Notices — `direct_acquisition_scraper.py`'s module docstring documents the 2026-08-31 reconnaissance that couldn't find this endpoint because its backing service lived in a JS chunk unreachable from the two bundles fetched at the time; `notice_scraper.py`'s own docstring documents the 2026-09-08 follow-up that found it in a since-changed, more consolidated site bundle — read that one before assuming any e-licitatie.ro endpoint name, including for the one field, award criterion, it still couldn't locate), and `municipal_scrapers.py` (direct feeds for București, Timișoara, Constanța; Cluj-Napoca and Iași are covered by `infra_scrapers.py`'s `UrbanismAcScraper`/`CountyHclScraper`). `municipal_batch1.py` extends that to four more regional hubs — Brașov, Craiova, Ploiești, Galați — and is worth reading before adding a fifth: all four were probed live first and turned out to run **four different architectures**, which is why they share only an error contract and not a parser. Brașov is a server-rendered Bootstrap accordion that is by far the richest municipal source in the codebase (notice number, the authority's own CIF, CPV code, Romanian-formatted value, bid deadline and award criterion, all from the listing page); Craiova is a custom PHP CMS whose titles carry a status prefix the portal adds itself (`Atribuita - `/`Anulata - `), parsed into a real `procurement_stage` and stripped from the title so one contract doesn't read as two projects once awarded; Ploiești is WordPress with genuine custom post types (`hotarari` — 12,198 HCLs — and `anunturi`) and deliberately does *not* subclass `wp_json_common.WordPressCategoryScraper`, whose `?categories=` query a custom post type doesn't answer; Galați is IBM/HCL Domino `.nsf`, the same platform family as Iași's `CountyHclScraper`. Two traps that cost a debugging round here and would cost another: Galați serves its **entire 4,915-row archive in one ~5MB document** (hence `MAX_ROWS` and a 1440-minute interval — an uncapped parse floods the feed with one municipality's back-catalogue), and its per-row text begins with a category label the portal repeats across hundreds of rows (`Anunț public`, `Anunt important !!`) rather than a subject, so the title must come from the prose *after* the `Data:` marker or every row lands with the same name and nothing for keyword matching to bite on. Ploiești has the mirror-image problem: an HCL's own title is only its number (`HCL 364/2026`), so the subject is lifted out of the decision's preamble (`referitor la` / `prin care se propune` / `privind`) and appended. Results are scored by `ai_refinery.py:IntelligenceRefineryEngine` (evidence-based 0-10 scoring — see `STAGE_PROFILES` for the procurement-funnel weighting, including a deliberately negative weight for already-`awarded` **and** `cancelled` results so closed procedures don't outrank live opportunities).

`notice_scraper.py` is also a case study in why this codebase insists on verifying reconnaissance live rather than trusting a plausible-looking name: its own first candidate, `api-pub/AdvNoticeCommon/GetAdvNoticeList/`, is real, live, and public — and is a completely different SEAP feature, confirmed only by also fetching its notice-type enum (`api-pub/comboPub/getSysAdvertisingNotices/`) and finding it returns "Informare publicare la JOUE"/"Anexa 2"/"Achizitii directe", none of which is a Contract or Simplified Notice. The endpoint that *is* CN/SC, `api-pub/NoticeCommon/GetCNoticeList/`, sits on a controller the prior session had already found (`NoticeCommon`) but assumed was only a per-record section viewer. `e-licitatie.ro`'s own bot mitigation silently drops connections (TLS handshake succeeds, then no HTTP response for 20-45s) under rapid repeated requests and recovers after roughly 15-20s — sharper than what DA/MC's own reconnaissance saw, and worth knowing before concluding an endpoint doesn't exist just because one probe hung.

A second, older `src/` pipeline used to sit alongside this one — a complete parallel implementation with its own SQLite store, its own scrapers and its own multi-tenant matching engine, reachable only from four developer CLI scripts and never from the deployed API. It was deleted along with multi-tenancy; if you find a reference to `src.`, `main.py`, `test_ai.py`, `run_full_cycle.py` or `system_health_check.py` anywhere, it is stale.

`procurement_notices.py` is a second, richer persistence path that runs *alongside* (not instead of) the lean `opportunities` table above: a Pydantic V2 `ProcurementNotice` model (contracting authority, financial breakdown, award details, timeline, attachments, `award_criterion`) written by `direct_acquisition_scraper.py` and `notice_scraper.py` into `procurement_notices` and `seap_ingest_state` (defined in `schema.sql`). DA, CAN, CN, and SC populate it; only MC still doesn't, since market consultations genuinely carry no CPV/value/award data at that stage — the schema stays ready for it regardless. `award_criterion` is itself a case of that same "ready before populated" convention cutting both ways: `notice_type` accepted all five SEAP categories long before CN/SC existed, and now `award_criterion` exists as a column with a confirmed real enum (`api-pub/comboPub/getSysAwardCriteriaTypes/`) behind it, but no scraper has found the per-notice endpoint that says *which* value a given CN/SC actually uses — see `notice_scraper.py`'s docstring before spending time re-deriving that Section-IV/Section-II endpoint search from scratch. Its `fingerprint()` (SHA-256 of notice_id+notice_type+estimated_value) is a content-change marker, not the dedup key — the actual UPSERT conflict target is `(notice_id, notice_type)`, since the fingerprint changes whenever a notice's value legitimately updates and using it as the identity would insert a duplicate row per update instead of revising the existing one. `split_cui_and_name`'s regex accepts both `"CUI Name"` (DA/CAN's `contractingAuthority`) and `"CUI - Name"` (`notice_scraper.py`'s `contractingAuthorityNameAndFN`) — the second form was a real bug caught while building CN/SC ingestion: the original regex matched but left a stray leading `"- "` on every parsed name.

`scrapers/adapters/` is a polymorphic CMS-adapter framework for county/municipal portals, separate from the per-source scraper classes above: `BaseCMSAdapter` (`detect`/`extract_procurement_notices`/`extract_hcl_decisions`/`download_document`) is implemented once per *platform* (`IndecoAdapter` for Indeco Soft's ASP.NET WebForms postback grids, `SobisAdapter` for a JSON-API suite, `GenericPortalAdapter` as the WordPress-REST-API-then-raw-HTML catch-all) and reused across every county confirmed to run it, rather than one bespoke scraper class per county. `scrapers/config/county_registries.json` binds each of Romania's 41 county councils to a `{base_url, platform}` pair — populated by live HTTP reconnaissance, not assumed: of the 41, live probing found 22 WordPress, ~13 unclassified "generic_html", and, importantly, **zero confirmed Indeco or Sobis deployments** despite both being named in the original spec as common platforms. The two counties whose homepage matched a "Sobis" text signature turned out on inspection to be an IBM/HCL Domino `.nsf` portal wearing a CSS theme called "Sobis" (same underlying platform as `infra_scrapers.py`'s existing `CountyHclScraper` for Iași) — registered as `platform: "domino_nsf"`, deliberately left unpolled since neither existing adapter matches that URL shape. Likewise the one ASP.NET-WebForms candidate for Indeco turned out to be Microsoft SharePoint (registered as `platform: "sharepoint"`, also unpolled) — `__VIEWSTATE` alone isn't a reliable Indeco signature, since SharePoint emits the same hidden field. Read `indeco_adapter.py`/`sobis_adapter.py`'s module docstrings before trusting either class against a new county: both are real, working code for their documented mechanics, just not yet matched to a live deployment among these 41. `scrapers/matrix/municipal_matrix.py:CountyRegistryScraper` is the single `BaseScraper` that bridges the registry + adapters into the orchestrator, fanning out under `asyncio.Semaphore(15)` and mapping each adapter's platform-agnostic notice dict onto `RawInstitutionalSignal` itself (domain classification and this app's field names are deliberately kept out of the adapters, which are meant to be reusable).

`ted_scraper.py:TedRomaniaScraper` (top-level of `scrapers/`, not `scrapers/matrix/` — it's a single national-relevance cross-border feed, not a per-institution matrix entry; note `elicitatie_scraper.py` is a comparable single feed that nonetheless lives under `scrapers/matrix/`, so don't infer a rule from either one's placement) adds live TED/OJEU cross-border notices naming Romania as buyer country, gated by `ENABLE_LIVE_TED`. It hits TED's genuinely public `POST /v3/notices/search` (no auth), filtering on `form-type IN (planning, competition, result)` rather than `notice-type` — the former uniformly spans every eForms subtype, confirmed by live trial-and-error against the API's validation errors — and restricts results to the `infrastructura`/`aparare`/`sanatate`/`energie` domains, dropping IT/HR/consultancy notices that also carry Romania as buyer. `utils/bnr_currency.py` supplies the EUR→RON rate (`https://curs.bnr.ro/nbrfxrates.xml` — not `www.bnr.ro`, which redirects away under that host's bot mitigation), 24h-TTL cached and falling back to a hardcoded, explicitly-dated real historical rate on fetch failure; RON-denominated TED notices (the majority for Romanian buyers) pass through unconverted. TED's eForms data carries no field referencing a national SEAP procedure number (verified against a real notice's full XML), so cross-referencing is a best-effort heuristic (`find_seap_cross_reference`, CPV-prefix + value-tolerance + buyer-name matching against `opportunities`, surfaced in `metadata` rather than auto-merged) instead of a real join.

`scrapers/money.py` is the single Romanian-money parser. Romanian sources render values as `1.234.567,89 lei` — dot for thousands, comma for the decimal — and getting that backwards does not raise, it silently produces a number wrong by three orders of magnitude that flows into `estimated_value_ron`, the score's value bands, the `min_value_ron` gate and the user's alerts. The same parser had been copy-pasted into five modules with a byte-identical regex, and a sixth was hand-written with the separators reversed (`'150.000'` → `150.0`, a 150k contract reading as 150 RON and sinking below every filter while looking entirely legitimate). Five identical copies is how the sixth got written instead of imported. One genuinely ambiguous case is resolved by a rule worth knowing: a Romanian thousands group is **always exactly three digits**, so `'1234567.89'` can only be a plain decimal while `'150.000'` cannot. `digital_scrapers._parse_value` is deliberately NOT folded in — its feed emits plain JSON decimals, and the convention is a property of the source, not of the country.

`workers/` is an in-process asyncio document-ingestion pipeline for heavy PDF attachments (scanned HCL budget annexes, CNAIR technical annexes) that would otherwise block a request thread or blow past a timeout — no Celery: this deploys as a single Render `env: python` service with no broker/second dyno, so it's two `asyncio.Queue()`s (`fast_text_queue`, `heavy_ocr_queue`) consumed by worker-pool coroutines in-process, same shape as the ingestion tick and `municipal_matrix.py`'s `asyncio.Semaphore`-bounded fan-out. **Three properties in `document_tasks.py` are load-bearing and each replaced a real failure mode; `tests/test_document_worker.py` guards all three.** (1) Document work runs on this module's *own* `ThreadPoolExecutor` (`_pool()`), never `run_in_executor(None, ...)` — the default executor is what `infra_scrapers.py:34` deliberately offloads CNAIR's 278-page PDF parse onto so `run_tick`'s `TICK_DEADLINE_SECONDS` stays enforceable, so a few multi-minute OCR threads there stall ingestion, which is precisely the starvation that offload exists to prevent. A test asserts over the AST (not a substring scan — this module's docstring names `run_in_executor(None, ...)` in prose) that no stage regresses to it. (2) `asyncio.wait_for` cancels the *await*, not the OS thread behind an executor call, so the timeout used to mark a document failed while its thread kept rendering — holding the full PDF and its pool slot, writing into a `TemporaryDirectory` the unwinding `with` block had already deleted. Both pipelines now take a `CancellationToken` (a `threading.Event` the sync code polls at page boundaries) that `_execute` sets when the timeout fires; the heavy path renders and OCRs in `OCR_PAGE_BATCH` batches specifically so those boundaries exist at all, which also caps peak temp-disk at one batch instead of the whole document. (3) Admission is budgeted in **resident bytes** (`QUEUE_MAX_RESIDENT_BYTES`), not queue items — each item holds an entire PDF, so a 64-slot count-bounded queue would still admit 2.5GB on a 512MB box. Over budget, the upload is rejected with a Romanian reason written onto its `document_extractions` row (which the frontend poller already renders) rather than dropped or left at `queued` forever. Queue depths, in-flight count and the byte budget are exposed as `document_workers` on `/api/v1/system/status` — counts only, since that route is public. `workers/pdf_preprocessor.py` classifies a PDF as digital-text vs scanned (pdfplumber sampling) and, for scanned pages, renders + OpenCV-preprocesses (deskew/denoise/adaptive-threshold) them; `workers/ocr_engine.py` wraps `pytesseract` (`lang="ron"`) and detects the Cap.1-4 legal-section headers via `text_utils.fold()`-normalized regex tolerant of OCR noise. **OCR cannot run on the current Render deployment**: `pdf2image` needs poppler-utils and `pytesseract` needs tesseract-ocr + the `ron` language pack, neither installed by `render.yaml`'s `pip install`-only buildCommand — both modules detect this at runtime (`shutil.which`) and degrade to `ocr_applied: false` with a specific `error_message` rather than crashing, same pattern as `CnairCfrScraper`. Results persist to the new `document_extractions` table (`document_extractions.py`/`.sql`, same `db.with_connection()` no-op-on-no-database convention as `procurement_notices.py`), surfaced via `POST /api/v1/addons/upload-caiet-async` (fire-and-forget `asyncio.create_task`, same pattern as `/api/v1/system/tick`) and `GET /api/v1/addons/document-extractions/{doc_id}`; `addons/caiet_analyzer.py`'s existing inline-upload path is untouched, with `load_extracted_text()` added as an alternate, additive source for `/api/v1/addons/analyze-caiet` (now also accepting `doc_id`/`notice_id`).

Ingestion runs on a soft per-tick deadline (`orchestrator.py:run_tick`, `TICK_DEADLINE_SECONDS`), skips sources whose own `poll_interval_minutes` hasn't elapsed (`db.is_source_due`) or whose circuit breaker is open (`db.get_circuit_state`, opens after 3 consecutive failures), and persists via `db.upsert_opportunity` — an overrun tick degrades to a partial run rather than being hard-cancelled, so `db.finish_tick` always records an outcome. Two things keep `is_stale` from going permanently true on Render's free tier: `.github/workflows/heartbeat.yml` (a GitHub Actions cron every 5 minutes, POSTing `X-Tick-Secret` to `/api/v1/system/tick` with a browser `User-Agent` — Render's backend edge, which runs on Cloudflare's CDN internally, can otherwise challenge headless-looking requests) and `api.py`'s own in-process APScheduler job that ticks once on startup and every 6 hours after.

### Postgres is the real backing store; the file cache is only a fallback

**`schema.sql` is the entire database and the single source of truth for it.** It replaced seven separate `*_schema.sql` files that had no documented apply order, defined three tables incompatibly across two files each, and had drifted from the live database badly enough to cause a login outage (an undeclared UNIQUE index on `user_profiles.email` that appeared in none of them). Apply it by hand via the Supabase SQL editor; it is safe to re-run. Two things in it are load-bearing and easy to misread: `saved_deals` is a *rename* of `product_bidding_deals` because the live table of that name was created with an incompatible shape and `CREATE TABLE IF NOT EXISTS` silently no-ops against it; and the RLS policies are **written but not `FORCE`d and are not the security boundary** — the API connects as the table owner, so `auth.uid()` is NULL and owners bypass RLS. Forcing it would take the backend offline instantly. All real access control is in FastAPI.

Its destructive section drops **two** generations of dead tables, not one. Besides the tenant-era tables (`tenants`, `tenant_products`, `product_bidding_deals`, `tenant_alert_dispatch_log`) it also drops the deleted `src/` pipeline's orphans: `raw_intel` → `structured_intel` (a two-stage scrape-then-refine store that the single `opportunities` table replaced), `scraper_logs` (replaced by `source_run_log`, which additionally carries poll intervals and circuit-breaker state — which is why the orchestrator can skip and back off and the old one could not), and `tenant_filters` / `tenant_dispatches` / `tenant_analytics_reports`. All six were verified unreferenced by any `.py`, `.sql`, `.ts` or `.tsx` in either project before being dropped. They survived the first pass because it enumerated only the tenant-era tables; if you find yourself writing a schema cleanup, enumerate from the **live** table list rather than from the files you happen to be editing.

`db.py` maintains a small `asyncpg` pool against Supabase Postgres (transaction-pooler-aware — `statement_cache_size=0` is set automatically when the connection string points at port 6543 / `*.pooler.supabase.com`, since the pooler can't hold per-session prepared statements). `api.py:_load_feed()` is the unranked, user-agnostic read path — kept deliberately separate from the ranked feed because `routers/analysis.py`'s market-trends endpoint is public and serves anonymous visitors, and the competitor-analysis benchmark needs the whole market rather than one user's slice: it calls `db.get_recent_opportunities()` (which accepts optional `start_date`/`end_date`/`counties`/`categories`/`min_value_ron`/`max_value_ron` filters, pushed down into a dynamically-built SQL `WHERE` clause) fresh on every call — there is no caching at this layer, so a filtered market-analysis request always re-queries live. Only when Postgres returns nothing does it fall back to `cache_engine.py:newsletter_store` (`NewsletterStore`, a JSON file on Render's ephemeral disk, rebuilt from scratch on every restart) — and the same filters are re-applied in Python to that fallback so a degraded response still honors the request.  The deal pipeline (`workflow_engine.py:ConcurrentWorkflowEngine`) is Postgres-backed (`saved_deals`, `deal_stage_history`, via `db.py`'s `get_deals_for_user`/`add_deal`/`update_deal`/`record_stage_transition`) with `CONCURRENT_DEAL_PIPELINE` kept only as an in-memory fallback — every read/write tries Postgres first and only touches the dict when `DATABASE_URL` isn't set or the migration hasn't been applied yet (detected via `asyncpg.exceptions.UndefinedTableError`), so don't assume the dict is authoritative.

`/api/v1/system/tick` dispatches the ingestion run as a background task and acks immediately rather than blocking on it — it used to await the full run (observed live: 1s to 373s+), which routinely exceeded the GitHub Actions heartbeat's client-side timeout and caused curl's retries to fire a second overlapping tick on top of the still-running first one. A module-level `asyncio.Lock` (`api.py:_tick_lock`) makes an overlapping call a no-op ("already_running") instead of a pile-up.

`db.py:connectivity()` answers whether persistence is configured *and* reachable, and is surfaced as the `database` block on `/api/v1/system/status`; `db.is_available()` backs the same distinction on the read path, so `_load_feed` now sets `degraded` when the database is unreachable rather than only when a query raises. This matters because every read in `db.py` degrades by returning `None`/empty for both "no database" and "database has nothing" — without the explicit check, a completely unconfigured `DATABASE_URL` reached the UI as a calm "0 opportunities" and the heartbeat as a bare `is_stale`, with nothing anywhere pointing at the actual cause. Connection errors are redacted before being returned over HTTP (`db._redact`), since asyncpg echoes the DSN — which carries the password — in some parse errors.

`cache_engine.py:global_cache` (`MemoryCacheEngine`, in-memory TTL, default 90s) is a separate, purely-response-level cache layered on top of the feed, keyed per user — invalidated by the background scraping job, not related to `newsletter_store`.

`workflow_engine.py:ConcurrentWorkflowEngine.get_pipeline_metrics()` (exposed at `GET /api/v1/me/pipeline/metrics`) computes weighted pipeline value using a stated stage-probability heuristic (not a trained model — the system has never ingested a real award result), plus real time-in-stage and funnel conversion rates derived from each deal's actual `stage_history` transition timestamps.

### Routers vs. inline routes

Most `addons/*.py` engines (independent, single-purpose, no shared base class: `caiet_analyzer`, `competitor_tracker`, `win_probability`) are invoked directly from routes inline in `api.py`. `business_eligibility`, `dossier_generator`, and `foia_generator` instead live behind `routers/eligibility.py` and `routers/drafting.py` — pulled out specifically so they map 1:1 to the frontend's standalone `/eligibility` and `/drafting` pages. `routers/drafting.py` also exposes `export-dossier-docx`/`export-clarification-docx` (streaming `.docx` downloads via `addons/docx_export.py`, python-docx) and an opt-in `use_ai_expansion` flag on the JSON generation endpoints that deepens the methodology/risk sections (`dossier_generator.py`/`foia_generator.py`'s `expand_with_ai()`) through the LLM chain described below — always additive, template output is a complete document on its own if no provider is configured. `routers/analysis.py` is not an addon wrapper at all; it reads `_load_feed()` directly (see above) and aggregates totals/breakdowns, with an opt-in `include_ai_report` flag for an LLM-synthesized strategic narrative. All three are mounted in `api.py` via `app.include_router(...)`. If you add a new addon-backed feature that has (or will have) its own frontend route, extract it into `routers/` rather than adding it inline to `api.py`.

`ai_copilot.py` is genuinely multi-provider with real sequential failover, not just a single configurable key: `list_llm_providers()` tries every configured provider (auto-detect order: groq, gemini, openai, xai — free-tier providers first, or forced via `LLM_PROVIDER`) and `complete_text()` walks the whole list, only giving up after every one fails. This is shared by `ProcurementAICopilot` (`/api/v1/copilot/chat`, inline in `api.py`) and by the document generators' `expand_with_ai()`. Note `render.yaml` names the xAI env var `GROK_API_KEY`, not `XAI_API_KEY` — `ai_copilot.py` reads both.

### There is no tenant — the user profile is the entity

A signup used to create a `tenants` row, exactly one `tenant_products` row, and a `user_profiles` row pointing at the tenant: a **1:1:1 chain modelled as a many-to-many**. It forced a `{tenant_id}` path param onto every route, an authorization layer (`require_tenant_membership`) whose entire job was checking that the id in the URL was your own, a browser-local "desk" object that existed only to remember which id to send, and it caused a total login outage. All of it is gone.

`user_profiles` **is** the user: `id` is the Supabase Auth uid (FK to `auth.users` with `ON DELETE CASCADE`, so GDPR erasure is one delete), and the row carries the matching criteria (`domain`, `target_counties`, `keywords`, `exclude_keywords`, `min_value_ron`), the alert settings (`alert_email`, `telegram_chat_id`, `min_alert_score`), an optional billing identity (`company_name`, `cui` — used only to prefill `/eligibility`, `/drafting` and the proforma), and `onboarded_at`, which is NULL until setup is complete and is what makes the frontend show the onboarding form.

Routes are `/api/v1/me/...`, and the user is taken from the verified JWT and **never** from a URL — which is why the authorization layer could be deleted rather than rewritten. One exception worth preserving: `db.get_deal`/`update_deal` still scope by `(user_id, deal_id)`, not `deal_id` alone. Deal ids are guessable and arrive in a request path, so without the owner in the WHERE clause any authenticated caller could advance a stranger's pipeline. That pair is what replaces the deleted membership check for that table.

**`db.upsert_user_profile_email` looks like tenant-era plumbing and is not — do not simplify it.** One human can hold several Supabase auth identities for one email (Google and magic link mint different `auth.users` rows; re-signup after deletion mints another), so a returning person can arrive with an id the table has never seen while their email is already on a row. A bare `INSERT ... ON CONFLICT (id)` sails past the id handler and hits the `user_profiles_email_key` unique index — which is exactly how every login started 500-ing. It re-points the existing row onto the current auth identity instead. `tests/test_auth_sync_identity.py` is its only guard.

Signup hardening: `MAX_USER_PROFILES` (default 300, read from the pre-existing `MAX_SELF_PROVISIONED_TENANTS` env var so the deployed value still applies) bounds the tick's per-signal matching loop; a `pg_advisory_xact_lock` closes a double-submit race; `security.enforce_onboarding_rate_limit` adds a 5/hour/IP budget on top of the global 180/60s; payload caps guard `matching_terms()`'s per-signal regex scan. Every signup and every capacity rejection fires an operator alert — self-serve with no approval step means zero visibility otherwise.

### The feed is a soft filter

`db.get_ranked_opportunities` returns the **whole market**, scored in SQL and ordered by relevance (weights in `db.RELEVANCE_WEIGHTS`). Nothing is hidden: an excluded keyword applies a large negative weight so the row sinks, never a `WHERE` clause that removes it. The previous behaviour returned only keyword matches, which meant a narrow profile saw an empty dashboard — indistinguishable from a broken product.

**Three filters on that query are deliberately HARD, and that is not a contradiction of the soft-filter doctrine above.** `get_ranked_opportunities` takes optional `authority_cui`/`procedure_type`/`award_criterion` and applies them as a real `WHERE`. The doctrine governs the *profile* — keywords, counties, domain, min-value sink a row rather than removing it, because a narrow saved profile must never render as an empty dashboard. These three are the opposite case: an explicit per-request narrowing the user just performed in the UI ("show me only this hospital's tenders"), where soft-filtering would be the bug. `tests/test_ranked_feed.py` pins the distinction by parsing the `WHERE` clause and asserting it mentions only those three columns and never a profile-derived one — the older `assert "WHERE" not in query` guard was a proxy that stopped meaning what it said once these landed. `opportunities.authority_cui`/`award_criterion` are promoted out of `metadata` (where DA/CAN/CN/SC already wrote `contracting_authority_cui`) onto real indexed columns purely because a JSONB key can neither take a B-Tree index nor be filtered efficiently per request; `procurement_notices` remains the canonical record and this is a denormalized read model. `text_utils.normalize_cui` is the single rule that keeps `authority_cui = $n` working — SEAP publishes the same authority both bare (`4374873`) and VAT-prefixed (`RO 14056826`), so both the write path (`ai_refinery`, and again defensively in `db.upsert_opportunity`) and the filter path normalise through it; storing two forms would make an exact-match filter silently miss a chunk of a user's own leads. `build_search_blob` also folds the CUI in so a free-text search finds an authority by fiscal code — deliberately *not* read by `matching_engine.evaluate`, since a tax ID in a keyword list should rank but never fire an email alert (the same asymmetry `entity_name` has always had).

**County matching is exact equality and therefore separator-sensitive**, which is why `db._county_key()` / `db._PG_COUNTY_KEY` exist alongside the plain fold rather than reusing it. Scrapers store `Caras Severin` with a space; the county's real name is `Caraș-Severin` with a hyphen, which is what a user types and what `fold()` faithfully preserves — so the two folded to `caras severin` and `caras-severin`, never matched, and that user's county silently scored zero on every row with no error anywhere. Both sides now normalise hyphens to spaces and collapse whitespace. The SQL half extends the `translate()` map by one character pair (`-` → space) and **both strings must stay the same length or Postgres rejects the call**, 500-ing every feed request; `tests/test_ranked_feed.py` asserts that balance and that the query still calls `_PG_COUNTY_KEY` rather than `_PG_FOLD`.

Keyword matching uses `opportunities.search_blob`, a pre-folded `title + summary + sub_category + entity` column written on upsert via `text_utils.fold()`. Folding on **write** is what keeps SQL and Python agreeing on what "equal" means; `unaccent()` at query time would need the extension, defeat any index, and disagree with `fold()` on the legacy cedilla forms (ş/ţ) Romanian institutional sites still emit. Whole-word matching is preserved with Postgres's `\m ... \M` boundaries — a substring test would let "sala" match "salariu".

**The word separator inside a multi-word term is a two-sided invariant, like the county `translate()` map above.** `text_utils.term_pattern` and `db._pg_word_patterns` both build a whole-word pattern by tokenising on `[a-z0-9]+` and re-joining, and they must join with the *same* thing or a keyword alerts but never ranks (or the reverse). They joined with `\s+`, which cannot match the hyphen the token was split on — so "Cluj-Napoca", "e-guvernare" and "CT-scan" compiled to patterns that could not match the very text they were built from, and since keyword evidence is a **mandatory** gate in `matching_engine.evaluate`, such a profile received no alerts at all, silently and permanently. Both now join on hyphen-or-space (`[\s\-]+` in Python, `[[:space:]-]+` in Postgres — `\s` is not portable inside a POSIX bracket expression), and `tests/test_ranked_feed.py` asserts the two stay in step. A keyword with no letters or digits at all ("***") produces no pattern from either, so `api.py:_validate_onboarding_payload` now rejects it at signup rather than letting it disable every alert.

Each lead comes back with a `match` object (`score`, `is_match`, `excluded`, `reasons[]`) so the UI can badge a row and say *why* it ranked. Three consumers apply `BRIEFING_RELEVANCE_FLOOR` instead of taking the whole feed — the 72h briefing, the copilot's context, and the CSV export — because without it each turns from "my qualified leads" into "the entire database, sorted".

**Alerts deliberately do NOT follow that ranking.** `matching_engine.RelevanceEngine.evaluate` keeps keyword evidence as a mandatory gate and `min_alert_score` still applies. "Everything matches a little" is fine for a ranked page and unacceptable for an inbox. The two answer different questions and are meant to differ.

Profiles are loaded **once per tick into a local** (`db.get_onboarded_profiles`) and passed down, never cached in a module-level dict. The old `TENANT_ORGANIZATIONS` cache had to be mutated in place (`.clear()`/`.update()`) forever after, because two modules bound the dict by reference at import — reassigning it would have left them matching against stale config with no error anywhere. A local has no aliasing hazard.

Cross-cutting concerns are separate small modules, not middleware classes. `security.py:SecurityGuard` now does two real things: `enforce_rate_limit` (180 req/60s per IP, in-process memory, wired in globally as `api.py:rate_limit_middleware` with a periodic stale-entry purge so the store can't grow unbounded) and `verify_access_token`, which verifies a real Supabase JWT via PyJWT. The per-IP key comes from `security.client_ip`, which reads `X-Forwarded-For` rather than `request.client.host`: `server.py` starts uvicorn with the default `forwarded_allow_ips="127.0.0.1"`, so behind Render's proxy `request.client.host` is the *same address for every visitor* — which silently collapsed all users, the heartbeat and every probe into one shared budget, so a single burst locked out everybody at once. `/api/v1/system/status` exposes `rate_limit.tracked_clients` (a count only, never addresses — the route is public) specifically so this is observable: a value pinned at 1 while several people are using the site is the signature of that bug returning. Supabase has migrated this project to asymmetric signing keys — confirmed live against its own JWKS endpoint, whose two active keys are ES256/EC, not RS256 (guides that assume RS256 are wrong for this project; the algorithm actually used is read from each key's own `alg` field via `jwt.PyJWK.algorithm_name`, never hardcoded). The primary path fetches Supabase's public signing keys from `SUPABASE_URL + /auth/v1/.well-known/jwks.json` through a module-level, cached `PyJWKClient` (mirrors `db.py`'s lazy connection pool — built once per process, not per request) and needs no secret at all. `SUPABASE_JWT_SECRET` (the project's legacy JWT secret from the Supabase dashboard — NOT `NEXT_PUBLIC_SUPABASE_ANON_KEY`, which is itself a JWT and can't double as another token's verification key) is kept only as a fallback, consulted solely when a presented token's own header says `HS256`: a session minted in the window before the project switched, which ages out on its own since Supabase access tokens are short-lived. Raises 401 on a missing/forged/expired/unrecognised token and 503 only if Supabase's JWKS endpoint itself is unreachable, rather than returning a fixed fake user. It is applied via `Depends(require_auth)` to every user-scoped, add-on, copilot, drafting and eligibility route (`security.py` exposes `require_auth` for the hard gate and `optional_auth` for routes that stay public but behave differently when signed in). Public by design: `/`, `/health`, `/api/v1/system/*`, `/api/v1/billing/plans`, and `/api/v1/analysis/market-trends` — the last via `optional_auth`, which serves aggregates to anyone but empties `top_opportunities` for anonymous callers. It only ever authenticates; the per-tenant authorization that used to be layered on top is gone with tenancy itself, because no route names anyone else's data. Two related hardenings shipped with it: `/api/v1/auth/sync` now takes the identity from the verified token instead of the request body (anyone could previously POST an arbitrary email and be handed a profile for it), and the feed's `is_subscribed` query param is gone entirely along with `FreemiumGatekeeper` — it defaulted to `true` and was trivially spoofable, so it never withheld anything; gating is off by decision until billing is real. `billing.py`'s `StripeBillingEngine` still has no Stripe SDK/API integration despite the name — it generates real HTML proforma invoices for manual bank-transfer payment, and `create_checkout_session()` just returns a "proforma required" response. `notifier.py:LeadAlertDispatcher` (Telegram + email fan-out for high-score leads, gated by each profile's `min_alert_score` and deduped via `db.has_alert_been_dispatched` — there is no Slack channel despite older docs mentioning one; unconfigured SMTP silently "succeeds" without sending) is real, working logic.

### Frontend

The app is split into standalone routed pages rather than one workspace component — each page owns its own data fetching and calls `lib/api.ts` directly: `/` (front page: masthead, live public stat tiles from `fetchMarketTrends()`, lead story, section index), `/login` (two-column screen, no Sidebar/Topbar chrome — Supabase Google OAuth or email magic link), `/auth/callback` (**client** component, not a route handler — see below), `/newsletter` (the core product: filterable/searchable pre-tender feed with a slide-over dossier per lead), `/eligibility`, `/drafting` (tabbed: technical proposal + clarification/FOIA, both with `.docx` export and an opt-in AI-expansion flag), `/analytics` (Copilot + 72h briefing, market profile, caiet scanner, price positioning — 4 tabs), `/analysis` (market-trends dashboard with pushdown filters; the only tool page that renders for anonymous visitors), and `/pipeline` (saved deals + `fetchPipelineMetrics`, with stage transitions).

**Every page whose data comes from an authenticated route is wrapped in `components/AuthGate.tsx`**, which distinguishes "not signed in" from "signed in but the backend rejected the session" (`AuthContext`'s `authError`). `/analysis` and `/` are the exceptions — they render public aggregates for anonymous visitors and hide only lead-level detail.

`lib/api.ts` is the sole HTTP boundary (no component calls `fetch` directly). Everything goes through one `apiFetch()` wrapper that selects the base URL, attaches `Authorization: Bearer <token>` read fresh from `supabase.auth.getSession()` on every call (never cached — a cached token goes stale after an hour and starts 401-ing), and decodes FastAPI's `detail` field into a typed `ApiError` so the real backend message (including the Romanian ones from `SecurityGuard`) reaches the UI. Routes that must stay anonymous pass `anonymous: true`; file downloads pass `raw: true` and go through a blob + object-URL helper, because an authenticated endpoint cannot be reached by a plain `<a download href>` — that is why CSV export and both `.docx` exports are buttons, not links.

**Response shapes are the backend's, not the old UI's assumptions.** `predict-win-rate` returns a qualitative `assessment`/`competitiveness_band`/`factors[]`, *not* a `win_probability_score` — the engine refuses to emit a probability it cannot evidence. `competitor-analysis` returns `observed_market`/`pricing.reference_points_ron`/`data_limitations`, *not* `benchmark.historical_avg_discount` or a competitor list. `analyze-caiet` signals a clean document with a single sentinel flag of severity `"OK"` rather than an empty array. The pre-refactor frontend read the older field names on all three, so those panels rendered blank or `undefined` in production; when touching these, verify against a live response rather than the surrounding TypeScript.

`AuthContext` exposes `user` (session) and `profile` (the server-owned criteria), plus `updateProfile`. There is no client-side company/desk model any more: a `BusinessDesk` abstraction used to keep a `localStorage` list of company profiles, each stamped with the backend tenant id to send with every request, plus three separate repair mechanisms to keep those ids valid. With one profile per user it had nothing left to do. `AuthContext` actively `removeItem`s the two retired keys (`ro_intel_user_desks`, `ro_intel_active_desk_id`) on load — nothing reads them, so otherwise every returning user carries dead JSON forever.

`components/EnterpriseModals.tsx` holds the globally-invoked modals over a shared `Modal` shell: `PricingModal`, `AccountSettingsModal`, and `ProfileCriteriaModal`. That last one replaced the desk manager and closed a real gap rather than porting one — the backend route for editing criteria existed and **nothing called it**, so there was no way to change what you monitor after signup short of deleting the account. It is opened from the identity strip at the top of the sidebar.

The feed UI reflects the soft filter: matched rows get an accent rail plus a `Badge` naming *why* they matched (from `lead.match.reasons`), and a "Doar potrivirile mele" toggle narrows to just those. **That toggle now starts on**, which is a reversal: defaulting to the whole market meant a user landed on all 500 rows immediately after entering their criteria, and reasonably concluded the criteria had been ignored. The soft filter is still the server's behaviour — nothing is hidden and one click shows everything — but the client opens on the user's own slice. The one exception is a profile that currently matches nothing: `/newsletter` detects that, falls back to the full market, and says so in a `Notice`, because opening on an empty page reads as a broken product rather than a narrow filter. The fallback runs once per mount and any manual toggle claims the decision, so it can never fight the user. The default sort deliberately does **not** re-sort by `opportunity_score`; that would discard the relevance ordering the feed was just built around.

**Județe are picked from a closed list, never typed.** `lib/format.ts:COUNTIES` holds the 41 counties plus București, rendered by `newsprint.tsx:ChipSelect` in both onboarding and the criteria editor. They used to be a comma-separated text field — a closed vocabulary asked as an open question, so `Cluj-Napoca`, `CJ` or a plain typo saved fine and then matched nothing, with no feedback. Diacritics and hyphens in that list are safe precisely because of the county normalisation above. `EnterpriseModals.tsx:DOMAINS` is now an alias of `CATEGORIES` rather than a second hand-copied copy of the same five domains, which would otherwise have drifted into a domain you can pick at onboarding but not edit afterwards. Note `digitalizare` is a real, supported domain that currently has zero rows — `digital_scrapers.py` emits it and `category_classifier.py` classifies into it; its sources just honestly return nothing so far. That is a data state, not a broken option, so don't "fix" it by removing it from the list.

`scrapers/cpv_taxonomy.py` gives the ingestion layer a real EU Common Procurement Vocabulary hierarchy rather than only the five-domain keyword guesser above. `CPV_DIVISIONS` (all 45 divisions) was parsed directly from TED's official eForms reference table, not hand-typed — WebFetch's HTML summarizer confabulated wrong labels for several divisions when asked for the same list in prose, so the table was built by curling the raw HTML and regex-extracting `<code>XX000000</code>`/`<p>label</p>` pairs instead, then cross-checked against a second primary source (the UK's consolidated text of Regulation (EC) No 213/2008) for the divisions both covered. `cpv_hierarchy()` decomposes any real 8-digit code into its Division/Group/Class/Category ancestors by pure string slicing — no lookup table needed for those tiers, since CPV's hierarchy is encoded in the code itself. `DIVISION_TO_DOMAIN` maps only a conservative subset of divisions onto the app's five existing domains (never introduces a sixth) and is deliberately incomplete: divisions whose label bundles unrelated concerns (75 mixes ordinary public administration with defence; 34 is generic transport equipment, not roads) are left unmapped on purpose rather than guessed, falling through to the keyword classifier exactly as if no CPV code existed. `category_classifier.classify_category`/`classify_with_evidence` now try `domain_from_cpv()` first — this closed a real bug, not just added a feature: `direct_acquisition_scraper.py` was feeding its already-fetched numeric CPV code into the classifier's free-text `description` parameter (an 8-digit number can never match a Romanian keyword, so it silently classified nothing), and `ted_scraper.py` fetched a real `cpv_code` from `classification-cpv` and then discarded it entirely, both fixed to pass it through the new `cpv_code` parameter instead. `opportunities.cpv_division`/`cpv_group`/`cpv_class`/`cpv_codes_all` (the last GIN-indexed) are derived from `cpv_code` at write time in `db.py:_cpv_hierarchy_fields`, the same "computed on every upsert so it can never drift" convention `build_search_blob` already uses — not a second data source. `opportunities.procedure_type` is a new, narrow, closed-vocabulary column (`ai_refinery.PROCEDURE_TYPES`) populated only where a live scraper genuinely states it (`cumparare_directa` for both direct-acquisition scrapers, `consultare_piata` for `ElicitatieLiveScraper`) — deliberately not the broader `procedure_type`/`tender_status`/`authority_cui`/`winning_bidder_*` set once proposed for this table, since those either duplicate the existing `procurement_stage` field (funnel position) or already have a canonical home in `procurement_notices.py`/`metadata` for the only two notice types that populate them (DA/CAN); adding mostly-NULL top-level columns with no ingestion path and a second source of truth for facts that already have one was judged not worth the schema noise. Wiring this up also surfaced that `DaAwardNoticeScraper` was the only stage-aware scraper that never declared `procurement_stage` in its metadata at all, so every CAN award notice was scoring under the neutral `"unknown"` profile (weight 0.6) instead of the deliberately negative `"awarded"` one (weight -1.0) meant to keep closed procedures from outranking live opportunities — now fixed alongside the CPV wiring.

CUI and company name are optional fields on the profile, used only to prefill the three places that name a real legal entity: `/eligibility`, `/drafting`'s dossier/clarification generation, and the proforma invoice. `billing.py`'s `ProformaRequest` still hard-requires them, so **a user who has not filled them in cannot generate a proforma** — the invoicing model (company CUI vs a private person's CNP) is still an unresolved product decision, not a bug to patch.

`components/Sidebar.tsx` (mounted once in `app/layout.tsx`, alongside `components/Topbar.tsx`) is the primary navigation: a persistent floating left sidebar on `lg:` and up (identity strip opening the criteria editor, routes grouped into "Ediția"/"Instrumente", account actions), collapsing to a floating header bar + slide-in drawer below that. Both return `null` on `/login`. `Topbar.tsx` renders a sticky breadcrumb + avatar bar above the page content on desktop only; it derives the current page's label from `Sidebar.tsx`'s exported `pageTitleForPath()`, so a new route needs an entry in `Sidebar.tsx`'s `NAV_LINKS` to get a correct breadcrumb, not just a new file under `app/`. `components/EnterpriseModals.tsx` holds the three globally-invoked modals (`PricingModal`, `AccountSettingsModal`, `WorkspaceDeskModal`) over a shared `Modal` shell; tool-specific dialogs live inlined in their page under `app/`.

`components/newsprint.tsx` is the shared component vocabulary (`Button`, `ButtonLink`, `Field`, `Input`, `Select`, `Textarea`, `Checkbox`, `Panel`, `StatCell`, `Badge`, `TabBar`, `Notice`, `EmptyState`, `Loading`, `DegradedBanner`, `PageHeader`, `SectionTitle`, `Eyebrow`, `Ornament`, …). Compose from it rather than restating shadow/color classes inline — it's the one place that has to change when the visual design pivots (see below), and every page already depends on that. `lib/format.ts` holds the RON/date/stage formatters.

### Design system: currently Neumorphism (Soft UI) — but this has already changed twice in one sitting

The visual design is being actively iterated on: this project went Newsprint (ink-on-paper editorial) → a dark violet-accent dashboard → the current cool-grey Neumorphic system, all on the same page structure and routing, in the same working session. **Don't trust this section's specifics without a quick check against `app/globals.css` and `components/newsprint.tsx` first** — another pivot may have happened since this was written, and the prose here will lag the code. What *doesn't* change across pivots: the token names (`paper`, `surface`, `ink`, `divider`, `editorial`, `stock-*`, `positive`/`negative`/`warning`) stay stable in `@theme` across redesigns specifically so a pivot only means editing `globals.css` + `newsprint.tsx` (and usually `Sidebar.tsx`/`Topbar.tsx`) rather than touching every page.

The current (Neumorphic) system: a single cool-grey surface (`#E0E5EC`) for the page and every card/button/input alike — `paper`, `surface`, and `surface-2` are all the *same* value, because this design has no concept of an "elevated" background tone. Depth comes only from paired light/dark box-shadows defined as real Tailwind utilities via `@utility` in `globals.css`: `neu-flat`/`neu-flat-sm` (resting extruded), `neu-lift` (hover, use with `hover:neu-lift`), and `neu-pressed`/`neu-pressed-sm`/`neu-pressed-deep` (carved-in wells, selected/active states, and inputs). An element is always either extruded or pressed — **never flat with a border**; `border-color` defaults to a very faint shadow-tinted rgba (`--color-rule`/`--color-divider`) reserved for internal content dividers (table rows, stacked sections within one card), not for defining a card's own edge. Accent is a single soft violet (`editorial` `#6C63FF`); semantic `positive`/`negative`/`warning` colors exist only as text/thin accent-bar color, never as a filled background, to keep the monochrome-shadow discipline. Radius is hyper-rounded and non-uniform by role: `rounded-3xl` (32px) for cards/panels/wells, `rounded-2xl` (16px) for buttons/inputs, `rounded-xl`/`rounded-lg` (12px) for inner elements. Fonts are Plus Jakarta Sans (`font-display`, headings) + DM Sans (`font-body`/`font-sans`) + JetBrains Mono (`font-mono`, tabular/data) via `next/font/google`.

`Sidebar.tsx`/`Topbar.tsx` are floating raised (`neu-flat`) panels with margin on every side, not flush chrome — a neumorphic shadow gets visibly clipped if the element touches the viewport edge, so both keep deliberate `p-4`/`m-3`-scale spacing around them rather than `w-full`/edge-to-edge. `.rule-grid` is now just `gap: 1.25rem` on a plain grid (each stat cell is its own self-contained raised card via `StatCell`); it used to draw hairlines through the parent background in the ink-on-paper system, so don't assume its current behavior from its name.

Mobile is a first-class target, not a fallback: all interactive elements are `min-h-[44px]`, wide content scrolls inside `.scroll-x` containers so the body never scrolls sideways, and the sidebar collapses to a floating header bar + slide-in drawer below `lg:`.

`next.config.mjs` no longer sets `typescript.ignoreBuildErrors` — type errors fail the build, which is the point of having them. `npm run build` is therefore a real check; keep it that way.

UI text is in Romanian (error messages, labels) — match that convention when touching user-facing frontend strings.
